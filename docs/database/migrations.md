# Database migrations

The relational schema is managed by **Alembic** (`backend/alembic/`), with models in `backend/app/db/models.py`.

## One schema authority
The application database is a standalone Postgres (docker-compose locally; any managed Postgres 16 in production) whose
schema is created and evolved **only** by Alembic. Supabase provides Auth and Storage, not the application database.

`supabase/migrations/` is **frozen**. It describes the legacy Supabase project's database and is kept for three things:
bringing the live legacy data into the shape the copy expects, the storage buckets and their policies, and locking
down the legacy public tables after the cutover (`docs/deployment.md`). New schema changes go into Alembic only.

The Alembic revision `0005` (the *cutover revision*) has exactly the schema of the final `supabase/migrations` state.
`backend/tests/test_migrations.py::test_cutover_revision_matches_supabase_migrations` applies both to empty databases
and fails if columns, types, nullability, defaults, constraints or indexes differ (the only allowed difference is the
Supabase-only FK `profiles.id → auth.users.id`). That is what lets `scripts/db/copy-data.sh` move the data with a
plain data-only dump/restore: load at `0005`, then `alembic upgrade head`.

## Everyday commands
```bash
make db                                  # local Postgres
make migrate                             # alembic upgrade head on the local database
make migration m="add notifications"     # autogenerate a revision from model changes; review it before committing
cd backend && uv run alembic downgrade -1
cd backend && uv run alembic check       # fails if models and migrations disagree
```

## Rules for revisions
- `CHECK` constraints are not autogenerated; add them to the revision by hand.
- Never change revisions up to `0005` or files in `supabase/migrations/`; the cutover depends on them staying equal.
- Review every autogenerated revision; autogenerate does not see triggers, functions or data changes.
- Every revision has a working `downgrade()`; the test suite runs upgrade → downgrade → upgrade on an empty database.
- Data-changing steps must be safe on a populated database (batches for large tables, `NOT VALID` + `VALIDATE` for new constraints).
- Never edit a revision that has been applied anywhere shared; add a new one.
