# Database migrations

The relational schema is managed by **Alembic** (`backend/alembic/`), with models in `backend/app/db/models.py`.

## Two migration tracks until the cutover
While the web app still talks to Supabase directly (until #22), production runs on Supabase Postgres and its
Supabase-specific objects (RLS policies, `auth.users` triggers, storage policies) live in `supabase/migrations/`.

| Track | Location | Owns |
|---|---|---|
| Supabase | `supabase/migrations/*.sql` | RLS policies, triggers that depend on Supabase Auth, storage buckets/policies, and (until cutover) the public tables themselves |
| Alembic | `backend/alembic/versions/` | The portable schema: tables, columns, constraints, indexes, `updated_at` triggers |

**Rule:** any change to a `public` table before the cutover is made in both tracks. `backend/tests/test_migrations.py::test_alembic_schema_matches_supabase_migrations`
applies both to empty databases and fails if columns, types, nullability, defaults, constraints or indexes differ (the
only allowed difference is the Supabase-only FK `profiles.id → auth.users.id`).

The baseline revision `0001` equals the Supabase schema after `20261009130000_enforce_matching_rules.sql`.

### Adopting Alembic on an existing Supabase database
Because the schemas are identical, an existing database is marked as already at the baseline instead of being recreated:

```bash
DATABASE_URL=postgresql+asyncpg://<user>:<password>@<host>:5432/postgres uv run alembic stamp 0001
```

From then on, apply later revisions with `alembic upgrade head`. (Use the direct connection string, not the pooler, for migrations.)

## Everyday commands
```bash
make db                                  # local Postgres
make migrate                             # alembic upgrade head on the local database
make migration m="add notifications"     # autogenerate a revision from model changes; review it before committing
cd backend && uv run alembic downgrade -1
cd backend && uv run alembic check       # fails if models and migrations disagree
```

## Rules for revisions
- Review every autogenerated revision; autogenerate does not see triggers, functions or data changes.
- Every revision has a working `downgrade()`; the test suite runs upgrade → downgrade → upgrade on an empty database.
- Data-changing steps must be safe on a populated database (batches for large tables, `NOT VALID` + `VALIDATE` for new constraints).
- Never edit a revision that has been applied anywhere shared; add a new one.
